# ws

For agents working on ws itself. (`FOR_LLMS.md` is the guide for an agent working *in* a workspace ws manages.)

**ws runs multi-repo work.** It began as a worktree manager: repos as bare clones, a read-only checkout of each default branch (the *ground*), a worktree per piece of work (a *capsule*). It also runs the work: a *mission* is a brief and the capsules it owns; agents (*crew*) work in them, an *orchestrator* agent decides what's next, and you review, approve and land from a web UI (`ws web`).

`MANUAL.md` is what ws does, for its users, and is kept current with the code.

## Build and test

```sh
just build     # the web UI into internal/web/dist, then bin/workspace. Always this, never go build -o
just check     # gofmt, go vet, go build ./..., and web/src/wire.gen.ts current
just wire      # web/src/wire.gen.ts again, from internal/web's types
just test      # go test ./..., then the web UI's tests (vitest)
just try up [seed...]       # try this build by hand: a fresh workspace in /tmp, seeded, its daemon and web UI up; prints dir, link, port, token and its ws
just try restart            # rebuild, and restart its daemon (same link)
just try down               # stop its daemon and remove it (it's also torn down when your session ends)
just test-workspace [dir]   # the same workspace, to keep: no daemon started, nothing torn down
just stories                # Storybook at localhost:6006: parts of the web UI drawn alone, every state side by side
just story-fixtures         # take the stories' missions again, from tries seeded for it
just shots [all]            # take the README's pictures again (all: FEATURES.md's too), of a try seeded with marketing
```

`ws eval` puts a role's prompt to fixtures, cases whose right answer is known, on a harness and model you name, and scores what comes back: for telling whether a change to a prompt, or another model in a role, does as well. It's off unless `WS_EVAL` is set, not listed and refused, and no agent ws starts is given the variable: it starts agents of its own, so it isn't for one to come on. It knows two roles (each one's `--help` says what a fixture is):

```sh
WS_EVAL=1 ws eval judge --pick claude:haiku internal/ops/testdata/judge/*    # the judge, on a step's work as its crew left it
WS_EVAL=1 ws eval orchestrator --pick claude:haiku \
  --before 'TRY_ROOT=$WS_EVAL_TMP scripts/try.sh up --no-build' \
  --after 'TRY_ROOT=$WS_EVAL_TMP scripts/try.sh down "$WS_EVAL_NAME"' \
  internal/ops/testdata/orchestrator/*    # the orchestrator, run for real on a mission a seed makes
```

The orchestrator's run is in a workspace made for it and removed after, which ws doesn't make: `--before` and `--after` are yours, and `scripts/try.sh` is what makes one here (`just build` first: `--no-build` uses `bin/workspace` as it is). A fixture's seed is a script as a try's is (`scripts/seeds`).

`internal/web/dist` is built, not committed: it's gitignored but for its `.gitkeep`, which `go:embed` needs. A binary built without it (`go build` alone, or `go install`) has no web UI, and `ws web` says so.

## Looking at the web UI

A change to the web UI is looked at before it's done, light and dark. [shotta](https://github.com/brudil/shotta) takes the pictures, of a try's web UI, for you to read: it's run from `web/`, where `shotta.config.ts` finds this checkout's try and signs in to it (`WS_LINK` names another's link).

```sh
just try up marketing                # something to look at: Sorrel's workspace (or the seed that has what you changed)
cd web
pnpm shotta snap /team --agent       # a page, light and dark: the report on stdout names each picture, in pieces small enough to read
pnpm shotta snap /team --of 'role=heading[name="Team"]' --pad 24 --agent    # one part you changed, with a little of the page around it
pnpm shotta snap /team --profiles phone --agent                             # at a phone's width
pnpm shotta find --agent             # a flow: Find, opened and asked something (shotta list names them)
```

Read `passes[].shots[].tiles`, and `passes[].storyboard` for a flow: one picture of the whole way through it. What takes a click or a key to come to is steps, as JSON on stdin (`pnpm shotta snap --steps - --agent`, with `{ "goto": … }`, `{ "click": … }`, `{ "press": … }`, `{ "shot": … }`), or a flow of its own where it's worth looking at again: `<name>.shots.ts`, in `web/shots/` or beside the part it shows. When `ok` is false, `failure.message` and `failure.aria` (the page as roles and names, which is what a selector is written in) say why. After writing or changing a flow, `pnpm shotta check` says what's wrong with it, with no browser: don't run `tsc` on one. The browser is fetched once a machine: `pnpm exec playwright install chromium-headless-shell`.

`just shots` is the same tool taking the README's pictures (`scripts/shots.mjs`).

A change to how a kind of thing is styled (every text field, every button: a part moved into the library, a rule moved between layers) is checked by what the browser made of each, before and after: `web/scripts/looks.mjs` goes through a try's pages and dialogs (`looks.scenes.mjs` lists them) and writes down each thing's box and styles, at rest and focused, and `diff` says what moved. Nothing should, but what the change says it moves.

```sh
just try up marketing tweaks briefing files plugin-proposals
cd web
node scripts/looks.mjs snap before.json                  # text fields, unless --of '<selector>' says what
just try restart                                         # with the change made
node scripts/looks.mjs snap after.json
node scripts/looks.mjs diff before.json after.json       # and again with --width 390
```

It sees only what its scenes reach: add a scene for what a change touches that none does.

## Releases

Pushing a `v*` tag (`v1.4.0`; one with a `-`, `v1.4.0-rc.1`, is a prerelease) runs `.github/workflows/release.yml`: it builds ws with its web UI for darwin/arm64, linux/amd64 and linux/arm64, cgo on for code navigation, and publishes them as a GitHub release with checksums. A pull request that changes the workflow runs the builds without releasing. `ws upgrade` installs a release over the ws that's running (`internal/release`, which reads the same assets and `checksums.txt` as `scripts/install.sh`: change what a release publishes, and change both); a daemon restarts onto it once nothing's at work (`internal/daemon/restart.go`). The daemon looks once a day for ws's latest release, and for each plugin's that was installed from a repo (`ops.CheckUpdates`, from `internal/daemon/loops.go`): the web UI says what's out, and Settings' About upgrades (`ops.UpgradeWS`, the same `release.Upgrader` as `ws upgrade`).

What's new after an upgrade is written by hand, one file an entry in `internal/whatsnew/entries/` (its README says how), and only where someone asked for one: don't add an entry to a change unasked. Which release an entry is in is its tag's to say: `scripts/whatsnew` works it out from the commit that added it, for `just build` and for a release's build, which also puts a release's entries at the top of its notes and its pictures among its files. The daemon keeps the release last seen (`ops.WhatsNew`), and the web UI says what's new since, once (`web/src/shell/WhatsNew.tsx`).

## How it's layered, and where it isn't

- **The domain packages are leaves.** `mission` imports nothing of ws but `store` (and `git`, `slug`); `conversation` and `review` import `mission`, and `page` imports `conversation` (a cell is one); `harness` imports nothing of ws's but `acp`. A rule about one store is in that store's package (where a thread on a document is anchored, when a cell's stale, which passes a page has), not in `web` or `ops`. Nothing below `cli` prints: packages return data and `cli` formats it.
- **What a harness can do is data:** `harness.CapsOf(name)` (how its crew are held, where their transcript is, which roles it can play). Ask that, not a type assertion or its name.
- **`internal/ops` is the application layer.** An operation that spans two domain packages is written there once, takes who's asking (`ops.Actor`) and checks what they may do, and returns what happened as data with a sentence (`String()`), or one of its errors (`ErrNotFound`, `*Invalid`, `*Refused` with a code, `*Upstream`), which `web.writeError` maps to a status. Missions and stages are there (accept, answer, dismiss, state, brief, title, attach, detach), capsules (lift, dock, burn, land: in process, never by running `ws` again), crew's launch, adding, updating and removing a plugin, every write the web UI makes to threads, talk, pages, cells, passes, reviews and drafts, saving a document, the views the web UI reads, and answering a conversation (`AnswerConversation`: one loop, with a responder per `Conversation.What` saying which agent answers, what it's told and how its reply is read). A command loads one for its run (`loadOps`, or `LoadOps(dir)`), and works through it: there's no other handle on the workspace; the daemon opens one for its life (`ops.Open`), whose config is read again when `ws.toml` or `ws.local.toml` changes, and its jobs, loops, web UI and plugins all work through that one: nothing in the daemon loads another. `internal/cli` holds the cobra commands, which format what `ops` returns, and starts the daemon (`daemon.Run`), giving it what only the commands know (`daemon.Config`: their labels and words, ws show's views). `internal/daemon` puts the daemon together: the web server (`newWeb`), the plugin host, the job queue and its loops. A write to somewhere slow that a page needn't wait on (a reply in a pull request's thread, to GitHub) goes through the daemon's outbox (`ops.Options.Outbox`, `internal/outbox`): its owner says how each kind is sent and what's read again once it has been (`pulls.Service.SendBehind`), shows it on what it keeps until then (`withThreadWrites`), and says what was refused (`Unsent`); with no outbox (a command's), it's sent as it's made. A kind whose writes are made in order says so (`Halts`: a stack's reviews), and one that can't be sent twice says how to tell whether it got there (`Made`). It's not the job queue, which runs agents and drops what's waiting when a newer job asks the same. Add a new verb to `ops`, and call it from the command and the web UI. `internal/arch` tests which package may import which.
- **`web` asks one interface.** `web.Server.App` is a `web.App`, which `*ops.Workspace` is: every write a page makes, and every view it reads (`ops.Overview`, `Mission`, `Artifact`…), comes from it, as `ops`'s own types that `web` maps to its wire types (`web.WorkspaceOf`, `MissionOf`, `ArtifactContentOf`…). A handler that only reads a store (`conversation`, `mission`, `page`) reads it directly; none runs git or writes a store. `web` doesn't import `cli` or `workspace`, and neither `cli` nor `daemon` builds `web`'s wire types: the daemon's `newWeb` only composes the server. What `ops` is given (`ops.Options`) is where crew run (the host), where agents' work is started (`Jobs`: the daemon's queue in it, its socket from a command), the clock, the PR cache, the daemon's own plugins and the Team service. Web's tests run on a real `ops.Workspace` (`testOps`), wrapped in a `fakeApp` where a test says otherwise.
- **The web UI's types of the API are generated from `web`'s.** `just wire` writes `web/src/wire.gen.ts` from `internal/web`'s exported types, with the types of other packages they use, named with the package in front (`review.File`: `ReviewFile`), by [guts](https://github.com/coder/guts) (`scripts/wiretypes`). Change a wire type in Go, run `just wire`, and `tsc` says what in the web UI no longer fits; CI fails if the file isn't current. `web/src/api.ts` re-exports the generated types (or names one as its own, `MissionTask = Task`); the rest it still declares by hand, mostly because the Go has `string` where the web UI has a union of strings. A named string type with its constants comes out as a union: the store's own (`mission.State`), or, for a field the store keeps as a plain string, one in `internal/web/enums.go` whose constants are the store's names for its values. Move a type by making the Go say what `api.ts` does, then dropping it from `api.ts`. An exported name in `web` that isn't sent or taken goes in `notWire`.
- **A mission's state is worked out, not stored.** `mission.DeriveState` and `mission.Resolve` give the state and whose court it's in to every front end. Don't re-derive either in a view.
- **How a headline is drawn is worked out there too.** `mission.Cards` makes each headline a card: its tone, a title, a sentence, the one action meant to move it (first, the only one accented) and what comes after, the quiet ones last, with the step the plan waits at folded into a question's card. The page draws a card as it's given (`CardView` and `CardActs` in `web/src/mission/Mission.tsx`), and knows only how each act is done. A new kind of headline, or a change to what one offers, is a change to `internal/mission/card.go`; the court's table of tests checks every case's cards against the rule, and they're the stories' *Every kind* (`just stories`).
- **What ws records is in `.ws/ws.db`,** which only the daemon opens: each store speaks SQL for its own tables, a write is one transaction (`store.Write`), a command's statements cross `store.sock`, and a write names what it changed. What's written to be read stays a file (briefs, handoffs, pages' text, versions, transcripts), written before its row. `ws doctor` sweeps files no row has; `ws export` writes a mission out as files. A write that matters has its error checked.

## Conventions

- **Words.** Ground, capsule, lift, dock, burn, land, board, silo: use these, not worktree, branch, delete. `MANUAL.md`'s Concepts section defines them.
- **Comments say why,** in plain sentences.
- **Commits are semantic** ([Conventional Commits](https://www.conventionalcommits.org)): `type(scope): subject`, and a pull request's title the same, since it's what a squash merge keeps. The type is one of `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`, `ci` or `chore`. The scope is optional: the area changed, a package or the web UI's part (`land`, `daemon`, `web`, `review`). The subject says why, in a plain sentence, lower case and without a full stop (`fix(land): a landing the mission can't record keeps the capsule, and says so`). A change that breaks a config, a command or a stored record adds `!` after the scope and says what breaks in a `BREAKING CHANGE:` footer.
- **Tests are behavioural.** `internal/integration` has tests that run real commands against a throwaway workspace (`testutil.SetupWorkspace`). Prefer one of those to a unit test of a helper. They're a package for each part of ws (`capsule`, `mission`, `orchestrate`, `artifact`, `doc`, `review`, `workspace`), so `go test` runs them side by side: a package's tests run one at a time, as they share the process's environment and output. Each package's `TestMain` is `testutil.Main`, what they share is in `internal/testutil`, and what they stand in for of `cli`'s own is in `internal/cli/seams.go`.
- **Agents are told, not trusted.** A rule that matters (crew don't land, crew don't accept their own stage) is enforced by the verb, as well as said in the prompt.
- **A page follows what it shows with `useEvents(topic, …)`** (`web/src/api.ts`): told when it's followed (`hello`: fetch then, so nothing's missed) and on each change. Every topic a tab follows goes over its one socket (`web/src/socket.ts`, `internal/web/socket.go`: follow and leave a topic, told following, changed or refused), whose messages are wire types like any other. A topic is one of the server's hubs (`Server.follow`), named as the records name what a write changed (`tx.Changed`): a write to a mission or a conversation tells its followers at once (`watchRecords`), and what the records can't see is looked at only while it's followed (`keyedHub`'s stamp: a mission's files and capsules, a conversation's agent's steps). Nothing in the web UI reads a thing again on a timer, and nothing holds a stream of its own: the topics are the workspace's, Reviews', Team's, the plugins', GitHub's and the runs' (`runs`: told when one starts, comes up or ends, from a stamp that reads no process table, `runs.Store.Stamp`), and by key a mission's, a conversation's, a crew's session (`transcript:`), a run's output (`runlog:`, told what's written), a ground's or capsule's on the Files page (`worktree:`), an app's (`app:`), a document being edited (`doc:`), a crew's screen (`screen:`, the latest frame only) and a pull request's. Where the server needs to know a page is open (a Files page's worktree, an app, for the runs started from them, which last while someone's looking), following its topic is what says so: a page doesn't ask again to say it's there. A new live thing on a page is a topic, never a timer: a stamp that's cheap to take (a stat, a record read), a hub that looks at it only while it's followed, and, where the page holds what it shows and it changes often, a change worked out once for every follower. Where a page holds a thing (a conversation: `conversation/talks.ts`; a crew's session: `mission/AgentView.tsx`'s `useTranscript`, its changes the entries from the first that changed, read by the server as the file grows, `harness.TranscriptReader`), it's read whole once it's followed, and then told how it changes rather than that it has: the hub works out the change once for every follower (`keyedHub.change`; a conversation's is `ConversationOp`: its turns from where the page's differ, the rest of it as it now is, as of the records' change number, `version`), and the page applies it (`applied`), reading it whole again only when it can't (a change missed, or one the server couldn't work out). A change is what the server worked out, never something the page interprets: a page doesn't work out what a turn does to a conversation's state, any more than a view re-derives a mission's. A page left open as the daemon's ws is upgraded is the old ws's web UI: it says so (`UpdatedBanner`), and reloading it loads the new one's.
- **The web UI loads with `useLoaded`** (`web/src/load.ts`): its value and error, `set` for a write that answers with the value, `reload` for one that doesn't, and `soon` for what a load has so far. A load that sets several things begins with `useLatest()` and checks that it's still the latest before it sets anything: never set state from a `.then` unguarded. A hover card is `HoverCard` around a trigger (`web/src/ui/HoverCard.tsx`), or `FloatingCard` with `useHoverDelay` for what isn't a trigger of its own (a tick, a row, words the editor draws). A card is placed by react-aria (`useOverlayPosition`), from a rectangle it's told, so what it's placed by needn't be an element. What a card says is laid out with `HoverCardHead`, `HoverCardTitle`, `HoverCardLine`, `HoverCardSaid`, `HoverCardLinks` and `hoverCardLinkClass`, and what it says of a thing is that thing's own part, with a story (a mission's crew: `MissionCrewCard`).
- **The web UI is built from a library of parts** in `web/src/ui`: `Button` (and `buttonClass` for a link that's an action), `Chip` (`chipClass`), `Count`, `PageHead`, `GroupHead`, `Summary` and `SummaryRow`, a list's `Rows` and `Row` (its link takes `rowLinkClass`, its status `rowStatusClass`; in it `RowMain`, `RowLine`, `RowTitle`, `RowSub`, `RowMeta`), with `Icon` and `Spinner` (the arc that turns: never an Icon given a class to spin), `Keys` (a key or a chord: `mod+⏎` reads ⌘⏎ on a Mac and Ctrl+⏎ elsewhere), `Copyable` (a ref, path or command that copies itself; `icon="over"` or `"inline"` for where its icon sits), and what a page says when something's wrong or there's nothing to show: `Callout` (a tinted panel in a `tone`, with a `title`, words and `actions`; `big` for one that leads), `Banner` (one line in a tone across the top of something, in danger unless it says otherwise, with what's pressed as its `actions`), `ErrorCard` (what didn't load, with `retry`), `Empty` (a place with nothing in it: an icon, a `title`, a sentence, an `action`, a `foot`; `big` and `done` for one that's a page's whole news), `Loading` and `Skeleton`. What's said in passing is `toast()` (`ui/toast.ts`), drawn by `Toasts` as `ToastPill`s. Where something stands is a `Status`: an icon and its words in its tone, or the icon alone (`iconOnly`, the words its tooltip), given what `ui/statusOf.ts` works out of a mission's headline, its state or crew; an icon in a tone that says nothing (a pin's kind, a mission's lead) is a `StatusIcon`, never a span with a status's class. A time is a `Time` (`as` a `stamp`, `relative`, an `age` or the `clock`, with the exact time on hover), and how a time reads is `ui/when.ts`. What an agent wrote, in a line of the words around it, is `Inline` (`lines` cuts it to so many); the same with no markup, for a title, is `plain` (`ui/text.ts`). The names in an `Inline` are drawn as refs because it says `data-refs`, which is what the refs' rules go by: a list of `RefTag`s that isn't in one says it too. An agent's steps are `Calls` (folded under their count, or `open`, with `tail` for a run going now), each a `CallLine`, which opens on what came back: an edit as an `EditDiff`, its todo list as `Todos`. A run going now is a `Doing`, one line that says what it's at, and `TypingDots` are the three dots of an agent at it. A hook pages share is a file named for it (`useTitle`, `useAutosize`, `useMedia`, `useDraft`). A page uses them, never their look by hand: not `<button className="ghost small">` but `<Button variant="ghost" size="small">`, not `<span className="chip tone-done">` but `<Chip tone="done">`. A look two pages share is a part of the library, with a story beside it (`Button.stories.tsx`, under *Components* in `just stories`) that draws each of its variants; those stories draw from props, as there's no mission in them. What's done to text shown is in `web/src/ui/text.ts` (`clip`, `capital`, and `humanError` for a server's error as a sentence), and the page's scroll is `pageScroller()` (`ui/scroller.ts`): use those rather than writing them again.
- **A part someone presses, opens or types in is react-aria's, in ws's look.** `Button` is `react-aria-components`' button with ws's classes and ws's defaults, and takes what a page would say to the browser's (`disabled`, `onClick`, `title`, `type`), so a page needn't know which it is; it's also what a menu or a popover opens from. Its `title` is a `Tooltip` (as a `ToggleButton`'s and a `Segment`'s are); words alone that have more to say keep the browser's `title`. A button that can't be used now is `disabled` when there's nothing to say of it (something's being sent), and `unavailable="why"` when there is: it looks disabled but can still be pointed at and focused, its tooltip says why, and pressing it says why again in a toast (`toast`, `ui/toast.ts`) and does nothing else. `Segmented` and its `Segment`s are one of a few, always one chosen (a width, a diff's layout): `value` and `onChange`, with `size="small"` and `fill`; `segmentedClass` and `segmentClass` are its look for a track that can't be one. `ToggleButton` is on or off by itself (a panel shown, a filter on): `pressed` and `onChange`, a Button's look, in the accent while it's on. Its words don't change with it: a button that says what pressing it does (Show past, Hide past) is a `Button`, with no `aria-pressed`. `Popover` is a button and what it opens beside it (`trigger`, `placement`, an `aria-label`); keys typed in it are its own unless it says `pageKeys`. `Menu` is a button and the list of things to do it opens: `MenuItem`s (an `id`, a `textValue`, `tone="danger"`), their words in `MenuText`, in `MenuSection`s with `MenuSeparator`s between, and a `foot` that isn't an item. A context menu is the same list opened at the pointer by the other button of the mouse: there's one for the whole page (`ContextMenuProvider`, around the app in `main.tsx`), and a part says what its menu holds with `useContextMenu()`, whose `menu(label, () => items)` is an element's `onContextMenu`; with nothing to hold, or while words are selected, the browser's own opens. A row that goes somewhere takes `useThingMenu()` instead (`web/src/shell/ThingMenu.tsx`): `onContextMenu={menu(to, title)}` gives it what Find can do to the thing it goes to (`actsFor`, `web/src/shell/acts.ts`), done by the same code as Find's (`web/src/shell/perform.ts`), and Open in new tab, which the browser's menu would have had. Something new to do to a mission, a conversation, an artifact or a pull request goes in `acts.ts`, and is then in Find and in every row's menu. Pin it and Unpin it are there too, for each of them (a write of your pins, from anywhere, is `web/src/shell/pins.ts`). `Select` and its `Option`s are a dropdown: the size of a text box, or `size="small"` (a button's) or `"tiny"` (in a line of words), and `fill`. `Modal` is what's over a dimmed page, which is inert while it's open, with the focus kept in it: a finder is one, with its own look as `className` (and `escape={false}` where Escape is its own to hear). `Finder` is a Modal with a text box over a list picked from by typing (`value`, `onChange`, `count`, `onPick`, its rows `FinderRow`s by `index`): the cursor, its keys and what the text box says of it are its own, by hand. `Dialog` is one with a head, drawn while it's open (`title`, `onClose`, `wide`, `bare`), with `DialogText` and `DialogActions` in it; `confirm()` asks before something that can't be taken back (`ui/Confirm.tsx`). An open dialog makes the rest of the page inert: what's drawn over it from elsewhere (a hover card, the toasts) says `data-react-aria-top-layer`. `Tabs` and its `Tab`s are the row of words over the views of one thing, the one shown underlined (`value`, `onChange`); what a tab shows is the page's to draw, a `role="tabpanel"` with an `aria-label`, its id given to the Tabs as `controls`. `Switch` is a setting that's on or off, changed at once (`on`, `onChange`, an `aria-label`). `Checkbox` is a box ticked or not with its words as its children (`checked`, `onChange`), laid out by the class a page passes. `RadioGroup` and its `Radio`s are one of a few down a column, each with words that say what it means (`value`, `onChange`, an `aria-label`). `Input` is a text box, and takes what the browser's input takes; a page that draws one without its box styles it by a class, or as the input in its bar. `TextArea` is the same for more than a line (it grows with its words by `useAutosize` on its ref). `Composer` is where something's written and sent (a reply, a message to crew, what should change): one box around the words and what's pressed, which grows as they're written, with the words the page's (`value`, `onChange`) and the key that sends them its own (`onSend`, `send="enter"` where ⏎ sends and not ⌘⏎); what's pressed is its children, in a bar under the words with a `hint` (the default), `layout="beside"` them for a small one in a panel, or `"corner"` for none, only the keys. `ListBox` and its `ListBoxOption`s are a list to pick one of (`value`, `onChange`, `empty`); a list of links a page's keys move through is `Rows`. `NoteCard` is something said about a place in what's read (a comment on a diff's lines, a thread in a document's margin, what a pass found): its states are props (`cursor`, `draft`, `resolved`, `found` and `blocks`, and `dense` for a margin's, which can be `hovered`, `folded` or `yours`), and in it are `NoteHead` (what it is, then at its `end` a `NoteId` and what's pressed), `NoteStatus`, `NoteBody`, a `NoteThread` of `NoteTurn`s, and a `NoteHint` or a `ReplyBox` for what's next; `Excerpt` is a few numbered lines of a file. Where a card sits is the page's, by the class it passes. `Change` is what something would change, the lines as they read on red over the lines as they would on green (`was`, `now`, or `hunks` of them): `signs` for code, `wrap` for words, `struck`, a `title`, `gone` for what's said where nothing takes their place, and `bare` in a card that's a box already. `MoreLink` is words in the accent that lead to the rest of something ("3 more in Work", "Show all"): a link with `to`, a button with `onClick`. `Clamp` is something long cut short until the rest is asked for, to a height in em that fades at its foot (`tall`) or to a count of `lines`, with the way to the rest there only when there's more (`of` is what it's of, so it's measured again when that changes). `PageBar` is the bar over one thing's page (a mission, a conversation), which stays at the top over a rule: the way `back`, its `status`, its name (`title`, with `onRename` where it's renamed in place), what's beside it as children, and at its end what's done to it (`actions`) or, where the page has views of it, their `Tabs` on the rule (`tabs`, with `pageBarTabsClass`). A page with no views of its own doesn't get tabs to have some. `Crumbs` is the way back on a page with no bar: where it's in, small and quiet over its head (`steps`, the first with an arrow, a dot between the rest), or a path of the page's own pieces as its children, with `CrumbSep` between. `Turn` is one turn of an exchange with an agent, which every such exchange is drawn with (a conversation's page, crew's transcript, the brief's planner, the conversation beside a page, a cell): `by` you, an agent, ws or crew, yours a bubble to the right and the rest text to the left, with a `head` (a `TurnHead`: a `TurnAvatar` or crew's badge, who, when) or `dense` beside something else, where there are no heads; in it are its steps (`Calls`), its words (a `TurnSaid`, `written` for yours) and, while it's `running`, a `Doing`. A part with a look of its own that needs what a Button does (to open a menu, say) is `<Button variant="bare">` with its class. Only `web/src/ui` imports `react-aria-components` (`web/src/ui/aria.test.ts` checks, and lists the pages that still do, a list that only gets shorter): a page that needs a menu, a dialog or tabs takes the library's, and one that isn't there yet is added there, one part a file, with its module and a story. What react-aria's part drops and a page says (a `title`, `aria-busy`) is put back in the part, through its `render`, and has a test (`Button.test.ts`).
- **A part's styles are a CSS module beside it** (`Button.module.css` by `Button.tsx`, `Runs.module.css` by `Runs.tsx`), imported as `css`, its classes named for what they are in that part (`.row`, `.namesNote`: camelCase, read as `css.namesNote`) and scoped to it by the build (`Runs_row_x1y2z`). `cx` (`web/src/ui/cx.ts`) puts classes together, and a modifier with its condition: `cx(css.row, open && css.open)`. The cascade is in layers (`styles.css` says so first): `base`, the elements and a few utilities; `ui`, the library's modules, each wrapped in `@layer ui { }`; then everything unlayered, which is the pages. So a page that gives a library part a class of its own (`<Chip className="find-chip">`, styled by the page) is drawn over the part, whatever the selectors' weight: that's how a page places or spaces a part, never by naming the part's classes, which it can't. `web/src/styles.css` is what's left global, being moved out a part at a time: a part that's touched moves its rules into its module then. `main.tsx` imports `styles.css` before anything else, so the layers are in that order. `web/src/cssModules.test.ts` checks every class read from a module is in it, and every class in it is read: a module is typed as any name to a string, so a misspelt class is otherwise `undefined`, silently. Code that finds an element by a module's class can't name it in a string: use a `data-` attribute or a ref.

What's worked out of ws's data to give it is a function beside it, with tests (`mission/timeline.ts`'s `timelineOf`), or the page's own component that maps one to the other (`Stepper`). - **What's beside the page is a pane, by the thing's address.** `web/src/chrome/panes.ts` says which addresses have one (`paneAt`: a conversation, a mission, a document, a pull request), and `Beside` draws it: a component in `web/src/panes` that reads the thing (`MissionPane`, `DocumentPane`, `PullRequestPane`) and gives it to that section's part, which reads nothing (`MissionPeek` with `mission/peek.ts`'s `peekOf`, `DocumentPeek`, `PullRequestPeek`), under a `PaneHead` and in `PaneSection`s. A pane is for looking: what's done to the thing is its own page's. `z` peeks at what the pointer's on, or the row the keys' cursor is on (`chrome/usePeekKey.ts`): any link to an address with a pane, so a new list needs nothing but links, a `Row` that's `selected` for its cursor, and `data-peek="<address>"` on what goes somewhere without being a link. There's one peek: the next takes its tab (`peekBeside`, `chromeState.ts`). `C` begins a conversation there (`panes/NewTalkPane.tsx`, at `newTalkAt`): ws has none for it until something's said, and then it's that conversation, in its tab's place. A tab that isn't kept yet (the peek, a conversation not begun) is `passing`: its name is in italics.
